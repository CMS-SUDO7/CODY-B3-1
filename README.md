# CLI Mini Redis

Python의 `dict`, `set`, `collections` 없이 해시맵, 이중 연결 리스트, 최소 힙을 직접 구현한 학습용 인메모리 Key-Value 저장소입니다. 네트워크 통신과 파일 저장 없이 CLI에서 동작합니다.

## 1. 실행 방법

Python 3.8 이상만 필요하며 외부 패키지는 없습니다.

```bash
cd mini_redis_project
python3 main.py
```

종료는 `exit`, `quit`, `Ctrl+C`, `Ctrl+D` 중 하나를 사용합니다.

```text
mini-redis> SET name "Alice Kim"
OK
mini-redis> GET name
"Alice Kim"
mini-redis> EXPIRE name 10
(integer) 1
mini-redis> TTL name
(integer) 10
mini-redis> INFO memory
used_memory:13
maxmemory:0
evicted_keys:0
mini-redis> quit
```

테스트 실행:

```bash
python3 -m unittest discover -v
```

## 3. 내부 구조와 데이터 흐름

| 구조 | 저장 내용 | 목적 | 주요 복잡도 |
|---|---|---|---|
| `data: HashMap` | key → value | 실제 문자열 데이터 | 평균 조회·저장·삭제 O(1) |
| `lru: DoublyLinkedList` | 최근 사용 순서의 key | 뒤쪽 LRU 키 즉시 선택 | 이동·양 끝 삭제 O(1) |
| `lru_nodes: HashMap` | key → LRU 노드 | 리스트 노드를 즉시 찾음 | 평균 O(1) |
| `expires: HashMap` | key → 현재 expire_at | 활성 TTL 판별 | 평균 O(1) |
| `expire_heap: MinHeap` | (expire_at, key) | 가장 빠른 만료 조회 | push/pop O(log N), peek O(1) |

LRU 리스트의 `head`는 가장 최근에 사용한 키(MRU), `tail`은 가장 오래 사용하지 않은 키(LRU)입니다. `SET`과 성공한 `GET`은 키를 head로 이동합니다. 메모리가 넘으면 tail부터 제거합니다.

TTL은 lazy deletion을 사용합니다. 같은 키에 `EXPIRE`를 여러 번 적용하거나 `DEL`하면 힙에 과거 항목이 남을 수 있습니다. 그러나 `expires`에 기록된 현재 만료 시각과 일치하는 항목만 유효하므로, 오래된 힙 항목은 루트에 도착했을 때 버립니다. 따라서 힙 중간을 O(N)으로 검색해 지울 필요가 없습니다.

## 4. 명령어 요약

| 명령 | 정상 결과 | 중요한 규칙 |
|---|---|---|
| `SET key value` | `OK` | LRU 갱신, 덮어쓰기 시 TTL 삭제 |
| `GET key` | `"value"` 또는 `(nil)` | 성공했을 때만 LRU 갱신 |
| `DEL key` | `(integer) 1/0` | 데이터·LRU·활성 TTL 동시 제거 |
| `EXISTS key` | `(integer) 1/0` | 먼저 만료 정리 |
| `DBSIZE` | `(integer) N` | 만료된 키 제외 |
| `KEYS` | 번호가 붙은 키 목록 | 패턴 매칭·정렬 없음 |
| `CONFIG SET maxmemory bytes` | `OK` | 0은 무제한, 축소 시 즉시 LRU 제거 |
| `INFO memory` | 메모리 관련 3개 항목 | UTF-8 바이트 길이로 계산 |
| `EXPIRE key seconds` | `(integer) 1/0` | 0 이하는 즉시 삭제 |
| `TTL key` | N, -1, -2 | -1은 TTL 없음, -2는 키 없음 |

## 5. 공식 메모리 계산과 OOM

```text
used_memory = 모든 키에 대해 Σ(UTF-8 key 바이트 수 + UTF-8 value 바이트 수)
```

예를 들어 `SET name Alice`는 `name` 4바이트 + `Alice` 5바이트로 9바이트입니다. 한글은 UTF-8에서 보통 글자당 3바이트이므로 문자 개수와 바이트 수가 다를 수 있습니다.

새 단일 엔트리 자체가 `maxmemory`보다 크면 기존 값을 건드리지 않고 OOM을 반환합니다. 단일 엔트리는 들어갈 수 있지만 전체 합계가 제한을 넘으면 새 키를 MRU로 표시한 뒤 LRU 키부터 제한 이하가 될 때까지 제거합니다.

## 7. 초보자용 구현 순서

1. **이중 연결 리스트부터 만든다.** 노드 두 개를 연결하고 head/tail 변화 그림을 손으로 그린 뒤, 빈 리스트·노드 1개·노드 여러 개를 각각 테스트한다.
2. **해시맵을 만든다.** `hash(key) % capacity`로 버킷을 고르고, 같은 버킷에서는 연결 리스트를 순회한다. 작은 capacity로 시작해 resize가 실제로 일어나는지 확인한다.
3. **최소 힙을 만든다.** 배열의 부모 `(i-1)//2`, 왼쪽 자식 `2i+1`, 오른쪽 자식 `2i+2` 관계를 이해하고 숫자나 튜플을 넣어 오름차순으로 pop되는지 시험한다.
4. **기본 Redis 명령을 붙인다.** 먼저 SET/GET/DEL만 구현하고 `used_memory`가 저장·덮어쓰기·삭제 때 정확히 변하는지 본다. 이후 EXISTS/DBSIZE/KEYS를 추가한다.
5. **LRU를 결합한다.** 데이터용 해시맵과 별개로 key→리스트 노드 해시맵을 둔다. SET/GET 시 앞으로 이동시키고 tail 삭제를 확인한다.
6. **maxmemory를 결합한다.** 단일 엔트리 OOM을 먼저 검사한 뒤 데이터를 넣고, 전체가 초과하면 tail을 반복 제거한다.
7. **TTL을 결합한다.** 활성 만료 시각은 해시맵, 빠른 다음 만료 탐색은 힙으로 담당시킨다. 재설정된 과거 TTL을 어떻게 무시할지 테스트한다.
8. **CLI와 에러를 붙인다.** 핵심 로직과 입력 처리를 분리하면 테스트에서 `input()`을 다루지 않고 명령만 직접 검증할 수 있다.
9. **엣지 케이스를 테스트한다.** 빈 구조, 덮어쓰기, 한글 바이트, TTL 재설정, 만료 직후 GET, 메모리 제한 축소, OOM 시 기존 값 보존을 확인한다.

각 단계가 통과한 뒤 다음 단계로 넘어가면 여러 구조가 얽힌 오류를 한꺼번에 추적하는 일을 피할 수 있습니다.

## 8. 이 미션에서 알아야 하는 지식

### 인메모리 저장소가 빠른 이유

주 데이터가 디스크가 아닌 RAM에 있고, 키 조회를 평균 O(1)인 해시맵으로 처리하기 때문입니다. 단순히 “메모리라서”만은 아닙니다. Redis의 명령에 맞는 자료구조를 선택하고 네트워크·직렬화·메모리 할당 비용을 관리하는 전체 설계가 속도를 만듭니다. 이 프로젝트는 그중 자료구조와 메모리 정책을 축소해 보여줍니다.

### 해시와 충돌

해시 함수는 긴 문자열 키를 정수로 바꾸고, 나머지 연산으로 버킷 위치를 정합니다. 서로 다른 키가 같은 위치를 받을 수 있는데 이것이 충돌입니다. 체이닝은 같은 버킷의 항목을 연결 리스트로 묶어 해결합니다. 항목이 너무 많아지면 체인이 길어지므로 로드 팩터가 0.75를 넘을 때 버킷을 늘리고 모든 키의 위치를 다시 계산합니다.

### 평균 O(1)과 최악 O(N)

해시맵의 조회가 항상 O(1)인 것은 아닙니다. 해시가 고르게 퍼지면 체인이 짧아 평균 O(1)이지만 모든 키가 한 버킷에 몰리면 O(N)입니다. 반면 이중 연결 리스트의 “이미 알고 있는 노드” 삭제·이동은 연결 포인터 몇 개만 바꾸므로 O(1)입니다.

### LRU에 자료구조 두 개가 필요한 이유

연결 리스트만 쓰면 사용 순서는 관리할 수 있지만 특정 키의 노드를 찾는 데 O(N)이 듭니다. 해시맵만 쓰면 키는 빨리 찾지만 사용 순서를 알 수 없습니다. 해시맵으로 노드를 O(1)에 찾고, 이중 연결 리스트로 순서를 O(1)에 바꾸는 조합이 필요합니다.

### 힙이 TTL에 적합한 이유

전체 키를 매번 훑으면 다음 만료 키를 찾는 데 O(N)이 듭니다. 최소 힙의 루트에는 항상 가장 이른 만료가 있어 O(1)에 확인하고 O(log N)에 추가·제거할 수 있습니다. lazy deletion은 힙 중간 삭제 비용을 피하는 대신 잠시 유효하지 않은 항목이 남는 공간상의 대가를 지불합니다.

### 능동 만료와 지연 만료

이 구현은 명령 실행 시 힙을 확인하는 지연 만료 방식입니다. CLI에 입력이 전혀 없으면 만료 시각이 지나도 즉시 코드를 실행하지 않지만, 다음 명령 전에 만료 키를 정리하므로 사용자는 없는 키로 봅니다. 실제 Redis는 접근 시 만료 확인과 주기적인 능동 만료를 함께 사용합니다.

### UTF-8과 메모리

`len("한")`은 문자 수 1이지만 `len("한".encode("utf-8"))`은 3바이트입니다. 요구사항이 바이트 단위 제한이므로 반드시 인코딩 후 길이를 계산해야 합니다. 노드나 버킷의 실제 Python 객체 메모리는 공식 산정에서 제외합니다.

### 불변식과 테스트

불변식은 항상 지켜져야 하는 규칙입니다. 예를 들어 `used_memory`는 데이터의 바이트 합과 같아야 하고, 데이터가 있는 모든 키에는 LRU 노드가 정확히 하나 있어야 하며, 활성 TTL은 존재하는 키만 가리켜야 합니다. 기능별 예시만 테스트하지 말고 이런 불변식이 저장·삭제·만료·제거 뒤에도 유지되는지 확인해야 합니다.

## 9. 예상 질문과 답변

**왜 Python dict를 쓰지 않았나요?**  
이번 미션의 목표가 해시 계산, 충돌 처리, 확장 비용을 직접 경험하는 것이기 때문입니다. 실제 제품 코드에서는 검증된 내장 자료형을 우선 사용합니다.

**TTL 힙에서 DEL한 키가 바로 물리적으로 사라지지 않아도 되나요?**  
활성 TTL 해시맵에서는 즉시 제거됩니다. 힙에 남은 과거 기록은 더 이상 유효한 엔트리가 아니며 루트에 도착하면 폐기됩니다. 이것이 lazy deletion입니다.

**SET 때문에 메모리가 초과되면 방금 넣은 키도 제거될 수 있나요?**  
단일 엔트리가 제한보다 크면 저장 전 OOM입니다. 들어갈 수 있는 크기라면 방금 키는 MRU가 되고 더 오래된 키부터 제거됩니다.

**시간 복잡도만 좋으면 실제로도 항상 빠른가요?**  
아닙니다. 입력 크기, 상수 비용, 캐시 지역성, 객체 생성, 해시 품질, 메모리 사용량도 실제 속도에 영향을 줍니다. Big-O는 입력 증가에 따른 성장률을 설명합니다.

## 10. 구현상 의도적으로 단순화한 부분

- 실제 Redis 서버 프로토콜과 네트워크 통신은 없습니다.
- 데이터와 설정은 프로세스 종료 시 사라집니다.
- TTL 정리는 백그라운드 스레드 없이 다음 명령 실행 시 수행됩니다.
- `KEYS`는 패턴을 받지 않고 모든 키를 반환합니다.
- 실제 Python 객체의 메모리 오버헤드는 과제 공식에 따라 계산하지 않습니다.
